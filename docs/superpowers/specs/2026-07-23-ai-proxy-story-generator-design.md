# 《灯火未熄》本地 AI 代理故事生成设计

## 目标

把当前 AI 故事工坊里“用户手动填写 API 基础地址、模型名称和 API Key”的前端直连模式，改为“前端只填写故事内容，后端从本地环境变量读取模型配置”的本地代理模式。

本次设计的核心目标有三点：

1. 用户以后点击“生成新故事”时，不需要再手动输入 `API 基础地址 / 模型名称 / API Key`。
2. `AI_API_KEY` 不再进入浏览器，只保存在本地 Node 服务的环境变量中。
3. 公开 GitHub Pages 页面保留 AI 工坊入口，但在没有本地代理服务时，给出明确中文提示，而不是暴露接口配置表单。

## 选定方案

采用“前后端同仓、同项目内新增一个轻量 Node 本地服务”的方案。

前端仍然使用现有 Vite 单页应用；后端新增一个本地 Node 服务，负责读取 `.env.local` 中的模型配置，暴露单一接口 `POST /api/ai-story`，再把请求转发到上游兼容 `chat/completions` 的接口。

相比把代理逻辑塞进 Vite 开发服务，这种方式更适合后续独立部署，也更容易扩展成限流、模板管理和多模型切换。相比一开始就引入更重的服务框架，这个方案更符合“先本地跑通”的目标。

## 目录结构与启动方式

项目新增一个 `server/` 目录，负责本地代理服务。推荐结构如下：

```text
server/
├── index.ts            # 启动 HTTP 服务并注册路由
├── config.ts           # 读取和校验环境变量
├── aiStoryRoute.ts     # POST /api/ai-story 路由处理
└── aiClient.ts         # 调用上游 chat/completions 并返回文本
```

前端和后端的职责边界如下：

- 前端：保留现有剧情、AI 工坊界面、故事试玩和生成结果展示。
- 后端：只负责读取本地配置、请求上游模型、解析和校验返回结果。

本地开发使用两个明确命令：

- `npm run dev`
- `npm run dev:server`

前端继续由 Vite 提供开发体验；后端单独监听本地端口。后续如有需要，再增加一个便捷脚本统一启动，但本次设计不强制引入并发脚本依赖。

## 环境变量

本地代理从项目根目录的 `.env.local` 读取模型配置。最小配置如下：

```env
AI_BASE_URL=https://你的兼容接口地址/v1
AI_MODEL=你的模型名称
AI_API_KEY=你的密钥
AI_SERVER_PORT=8787
```

规则如下：

- `AI_BASE_URL` 指向上游 OpenAI 兼容接口的基础地址，不要求用户在前端可见。
- `AI_MODEL` 由本地后端统一决定，前端不再暴露模型选择。
- `AI_API_KEY` 只存在本地后端环境中，不写入浏览器本地存储，不透传给前端。
- `AI_SERVER_PORT` 默认可设为 `8787`；若缺失，可由后端使用相同默认值。

本次不要求把 `.env.local` 示例文件发布到公开站点，但建议实现时增加 `.env.example` 方便本地配置。

## 接口协议

本地后端只先暴露一个接口：

`POST /api/ai-story`

### 前端请求体

前端只提交真正属于“故事生成需求”的字段：

```json
{
  "brief": "故事需求",
  "protagonistName": "主角名字",
  "tone": "整体基调"
}
```

字段说明：

- `brief`：必填，对应用户描述的新故事需求。
- `protagonistName`：可选，留空时仍可沿用当前逻辑回退为“主角”。
- `tone`：可选，留空时回退为现有默认基调。

### 后端行为

后端收到请求后：

1. 读取并校验 `.env.local` 中的 `AI_BASE_URL / AI_MODEL / AI_API_KEY`。
2. 使用当前已经存在的中文系统提示词和用户提示词结构，组装上游 `chat/completions` 请求。
3. 调用上游兼容接口。
4. 从返回中提取 `choices[0].message.content`。
5. 解析可能带围栏代码块的 JSON 文本。
6. 继续复用现有故事结构校验逻辑，确保返回可直接喂给前端生成故事播放器。

### 成功响应

成功时，后端直接返回已经校验通过的 `GeneratedStory` JSON。

也就是说，前端在成功路径上不需要理解“代理层”和“直连层”的差别，只把响应当作现有生成故事对象使用。

## 上游兼容范围

本次只先支持 OpenAI 兼容的 `chat/completions` 上游接口。

这意味着代理服务内部仍沿用现有请求结构：

- `model`
- `temperature`
- `messages`

并维持当前的中文提示词约束：

- 都市雨夜
- 情感错位
- 2 到 3 个结局
- 没有绝对圆满结局
- 返回严格 JSON
- 节点数控制在 5 到 8 个之间

本次不同时兼容 OpenAI 官方新接口、Responses API 或多供应商自动切换，避免把第一阶段做重。

## 前端 AI 工坊改造

AI 工坊界面将从“连接配置 + 故事种子”双面板，收敛为“只输入故事相关内容”的模式。

### 删除的输入项

- `API 基础地址`
- `模型名称`
- `API Key`

### 保留的输入项

- `主角名字`
- `整体基调`
- `故事需求`

### 保留的展示区

- `最近生成`
- `试玩最近生成`

### 交互变更

- 点击 `生成新故事` 时，前端直接请求本地代理：
  - 默认地址为 `http://127.0.0.1:8787/api/ai-story`
- 前端不再保存浏览器侧连接配置，也不再展示任何敏感配置字段。
- AI 工坊页面需补充明确说明：
  - `生成新故事需要先启动本地 AI 服务。`

这样改完后，用户在工坊里只需要关心“要什么故事”，不再需要理解模型连接参数。

## GitHub Pages 与公开站点行为

当前试玩链接部署在 GitHub Pages 上，属于纯静态站点，本身不能运行本地 Node 服务。

因此公开站点上的规则明确为：

- 仍然显示 `AI故事工坊` 入口。
- 用户仍能进入工坊页面并查看介绍、最近生成故事等本地状态。
- 当用户点击 `生成新故事` 且没有可访问的本地代理服务时，前端提示：
  - `请先启动本地 AI 服务。`

本次不采用“在线站点隐藏工坊入口”或“禁用按钮不允许点击”的方案，因为显式提示更清楚，也更符合用户已经确认的行为预期。

## 错误处理

错误提示统一尽量转成面向用户的中文文本。

### 前端可识别的失败场景

- 本地代理服务未启动或无法连接
  - 前端提示：`请先启动本地 AI 服务。`

### 后端返回的失败场景

- 缺少环境变量
  - `本地 AI 服务缺少必要配置，请检查 .env.local。`

- 上游 HTTP 失败
  - `AI 请求失败（HTTP xxx）`
  - 若上游返回可读文本，则拼接到提示后面

- 上游返回内容为空
  - `AI 没有返回可解析的故事内容。`

- 上游返回的内容不是合法 JSON
  - `AI 返回的内容不是合法 JSON。`

- 上游返回的故事结构不符合游戏要求
  - `AI 返回的故事结构无效：...`

- 未知异常
  - `生成故事时发生未知错误。`

前端只负责显示这些错误，不再自己拼装底层接口配置或模型信息。

## 可复用逻辑

本次设计尽量复用现有已经存在的 AI 故事逻辑，避免重复实现：

- 复用当前的提示词生成逻辑
- 复用 JSON 围栏提取逻辑
- 复用 `GeneratedStory` 类型
- 复用故事结构校验逻辑
- 复用前端生成故事试玩流程和最近生成存档逻辑

也就是说，这一轮核心是“把连接方式从浏览器直连切到本地代理”，而不是重写整个 AI 故事系统。

## 测试与验收

需要补充以下验证：

### 后端单元测试

- 缺少环境变量时报错
- 上游 HTTP 失败时报错
- 上游返回空内容时报错
- 上游返回非法 JSON 时报错
- 上游返回结构不合法时报错
- 合法返回可成功解析成 `GeneratedStory`

### 前端组件/集成测试

- AI 工坊页面不再显示 `API 基础地址 / 模型名称 / API Key`
- 点击 `生成新故事` 时向本地代理路径发请求
- 本地代理不可达时显示 `请先启动本地 AI 服务。`
- 生成成功后仍可进入“试玩最近生成”

### 回归验证

- `npm test`
- `npm run build`

本次不要求在 GitHub Pages 上实际跑通在线 AI 生成，因为 Pages 静态环境不具备本地代理能力。上线验证重点是：

- 页面提示清晰
- 本地开发环境可以连通后端代理

## 不在本次范围内

- 在线公网可用的 AI 代理部署
- 多模型切换
- 多供应商轮询
- 自动重试和复杂限流策略
- 用户在前端切换接口地址或模型
- 管理后台
- 故事生成配额统计

这些内容应在本地代理模式稳定后，再单独拆下一轮设计。
